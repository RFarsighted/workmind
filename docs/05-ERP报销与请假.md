# ERP 报销与请假（模板五）实施计划

## 目标与当前状态

本模块让用户用自然语言填写报销或请假申请，由多个审批角色依次审核，并实时查看审批步骤和对话。申请及审批记录需要持久化，支持从历史列表打开完整详情。

后端已提供解析、审批流和历史接口；Vue 页面与 Pinia 状态已接入解析、审批进度、消息气泡和历史摘要。历史详情 API 已提供，当前前端尚未接入点击查看详情。共享历史不提供用户级隔离。

实现沿用仓库的 FastAPI、Pydantic、SQLAlchemy、Alembic、PostgreSQL 和 Vue 3/Pinia，并通过兼容 OpenAI Chat Completions 的 DeepSeek 接口完成 JSON 输出。模型输出须经 Pydantic 校验；费用合计和确定性的合规检查由服务端计算，不依赖模型自我报告。

## 表单解析与规则检查

- `POST /api/erp/parse` 接收 `{text, formType}`，其中 `formType` 为 `expense` 或 `leave`；成功返回 `{form}`，警告位于 `form.warnings`。请求缺少文本、类型无效、模型不可用或结构校验失败时返回明确错误。
- 报销表单包含 `type`、`reason`、`items`、`totalAmount` 和 `warnings`。每条费用明细包含项目名、金额、日期、备注、数量和单位；`totalAmount` 由明细金额求和得到。金额缺失或非正数、没有有效明细时禁止提交；非关键材料缺失作为警告展示。
- 住宿按每晚限额、餐饮按每次限额核对。无法从描述中可靠确定数量或单位时，不推测单价，生成待确认警告。规则默认值为住宿 800 元/晚、餐饮 500 元/次；用 `ERP_HOTEL_NIGHTLY_LIMIT` 和 `ERP_MEAL_PER_OCCASION_LIMIT` 配置。
- 请假表单包含假期类型、起止日期、自然日天数、工作日天数、原因和警告。起止日期须有效且结束日期不早于开始日期；没有日期也没有请假时长时禁止提交。只给时长时按 `Asia/Shanghai` 今天起算并加确认警告。工作日计算只排除周末，不加载法定节假日或调休日历。
- 病假未提供医院证明时显示警告，并由 HR 在对话中提醒；此情况本身不自动驳回。公司规则演示文本中的住宿标准同步为 800 元/晚，符合 `docs/local-run.md` 中的 RAG 校验步骤。

## 多角色审批与消息流

审批链按申请类型和金额/天数确定：报销依次由主管、财务审核，金额超过 5000 元时增加总监；请假依次由主管、HR 审核，超过 5 个工作日时增加总监。阈值可通过 `ERP_DIRECTOR_EXPENSE_THRESHOLD` 和 `ERP_DIRECTOR_LEAVE_WORKDAYS` 配置。边界采用严格大于：正好 5000 元或 5 个工作日不增加总监。

审批按角色串行执行。每个角色接收完整表单和此前共享的对话历史，消息限制为 80 字以内且不使用 Markdown。每个角色依次产生：

1. 审批人提出审查意见或问题（`question`）。
2. 申请人回应（`answer`），只能引用表单中已有的信息；缺少答案时明确说明材料未提供，不得编造事实。
3. 审批人给出结论（`decision`），以结构化 `approved` 布尔字段和简短意见返回。

住宿或餐饮超标、商务舱等明确违反规则的情况须驳回并说明原因。任一审批人驳回后立即停止后续审批，并持久化最终结果。结构化结论决定步骤状态，消息文案不通过关键词猜测结论。

`POST /api/erp/submit/stream` 接收 `{formData, formType, applicantName}` 并以 SSE 推送进度。正常事件顺序为 `start`、`plan`、每个角色的 `approver_start` 和三条 `message`、`approver_done`，之后继续下一角色，最后发送 `final`、`done`。模型或服务错误时先发送失败 `final`，再发送 `error`；已产生的消息保留，申请标记为失败。每次申请使用独立 ID 和局部对话上下文，避免并发串流。

## 持久化、历史与前端

使用 PostgreSQL 新增 ERP 申请表并通过 Alembic 管理迁移。记录至少包含唯一申请 ID、类型、申请人名称、表单数据、审批步骤、完整消息、最终结果、失败原因和创建/更新时间。状态为 `pending`、`approved`、`rejected` 或 `failed`；提交时先保存 `pending`，完成或出错后更新状态。

- `GET /api/erp/applications` 返回按创建时间倒序排列的历史摘要。
- `GET /api/erp/applications/{appId}` 返回该申请的完整表单、审批步骤、所有对话消息、最终结果或失败原因；未知 ID 返回 404。
- 前端使用现有解析、审批进度和气泡组件显示审批过程与历史摘要；收到失败 `final`/`error` 后展示中断状态、提示错误并刷新历史列表。完整历史详情接口已提供，详情页面尚未接入。
- 首版沿用仓库无登录的演示模式，历史对所有访问者共享，不做用户级隔离；不发送真实邮件或飞书通知。

## 验收场景

- 输入“上周去上海出差，高铁 800，住宿两晚 960，餐费 300”，解析出明细，总金额等于明细金额之和；住宿均价为 480 元/晚，不触发住宿超限。
- 住宿明细缺少晚数时出现待确认警告；每晚超过 800 元时规则检查触发超限并要求财务驳回。
- 报销 5000 元走主管、财务；超过 5000 元增加总监。请假 5 个工作日走主管、HR；超过 5 天增加总监。覆盖阈值边界和周末日期计算。
- 商务舱机票触发财务驳回；病假缺少医院证明时 HR 提醒，但规则本身不自动驳回。
- 审批消息按问题、申请人回应、结论顺序实时出现；申请人回应不包含表单以外事实；驳回后后续角色不启动。
- 并发申请的 ID、步骤和消息互相隔离；通过、驳回和中途失败记录均可从历史列表打开完整详情。服务重启后 PostgreSQL 中的历史仍可读取。
